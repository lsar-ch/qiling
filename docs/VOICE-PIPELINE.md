# DeskMate 语音对话链路

## 1. 目标

语音不是附加功能，而是 DeskMate 第一版的主要卖点之一。

第一版要先做到：

- 能听
- 能说
- 能打断
- 能判断简单问答与复杂任务
- 能把复杂任务转给后台 Codex 或其他 Agent

后续再升级为更完整的全双工体验。

## 2. 参考模式

Qwen-Audio-Agent 的公开架构给出一个很清晰的参考：

- 前台是实时语音入口
- 简单问题由前台立即回答
- 复杂任务通过 ACP 委派给后台 Agent
- 用户说话时可以打断正在播报的内容
- 长任务完成后会把结果播报回来
- 危险操作要先走语音确认

这说明语音链路不能只做“STT → LLM → TTS”，而应该从一开始就按“语音前台 + 任务后端”设计。

## 3. 推荐链路

```text
麦克风输入
  → VAD 检测
  → 唤醒 / 进入聆听
  → STT 转写
  → 意图判断
  → 简单问答 / 复杂任务分流
      → 简单问答：前台直接生成回复
      → 复杂任务：交给 Agent Router / Codex 后端
  → TTS 播报
  → 播报期间支持 barge-in
  → 任务结果回流
```

## 4. 第一版实现重点

### 4.1 先做稳的对话闭环

第一版不必强求真正意义上的双人同时说话，但要把交互模型设计成可以升级到全双工：

- 播报时麦克风保持可监听
- 用户插话能中断当前播报
- 中断后立刻回到新一轮识别

### 4.2 先把任务分流做好

语音输入后先分两类：

- `simple_answer`
- `delegated_task`

前者由本地/当前会话直接回答，后者交给后端执行器。

### 4.3 先把状态回传做好

语音链路要能驱动挂件状态：

- listening
- thinking
- speaking
- executing
- awaiting_approval
- completed

## 5. 技术要点

### 5.1 VAD

VAD 用来判断：

- 用户是否开始说话
- 用户是否说完
- 播报期间是否发生插话

### 5.2 STT

第一版建议先选稳定、成熟、好替换的 STT 方案。
后续如果要追求更低延迟，可以再换成流式方案。

### 5.3 TTS

第一版只要求能播报，不强制情绪化和地区口音；但接口需要预留 `tone`、`emotion`、`speed` 和 `ssml` 等参数。

TTS 供应商可以由用户配置或替换。系统统一生成“文本 + 语气参数 + 挂件状态”，具体供应商只负责把这些参数尽可能转换成音频。

### 5.4 Barge-in

Barge-in 是全双工体验的关键基础。
意思是：

- 助理正在说话
- 用户一开口
- 当前播报立即中断
- 新输入轮次开始

这一步先做好，后续全双工才有基础。

## 6. 权限与确认

复杂任务里，以下情况必须经过确认：

- 删除
- 发送
- 支付
- 修改配置
- 任何高风险自动化

确认最好走语音和界面双通道。

## 7. 第一版建议

第一版语音目标建议定义成：

- 基础语音对话可用
- barge-in 可用
- 简单/复杂分流可用
- Codex 后端可接入

先把这条链路跑通，再升级成更强的全双工和多模态。
