## 0. 一分钟速览

- 症状：挂件画面仍显示，但窗口拖动、点击相关 IPC、气泡尺寸调整和自由走动停止，看起来像“挂件卡住”。
- 根因：Rust 新增的 `PositionMoveGate` 在**持锁期间调用需要主事件循环响应的 Tauri 窗口 API**。
- 死锁链：后台 `settle_worker` 持锁后调用 `outer_position()` 等主线程；主线程执行同步命令时又等待同一把锁。
- 证据：两次 `sample` 间隔后仍停留在完全相同的互斥等待栈，属于永久死锁，不是 CPU 卡顿或偶发延迟。
- 推荐修复：把 5 个会进入位置锁的同步 Tauri 命令改成 `async fn`，让锁等待发生在 Tokio 线程，主线程保持可响应。
- **不要直接删除 `PositionMoveGate`**：它用于阻止旧 settle/retry 覆盖新的 wander 移动；删锁会把此前“走 4 步退 3 步”的抖动带回来。
- 当前工作树已经包含大量动物移动改动；本轮只整理文档，**没有修改代码**。

## 2. 已搜集到的证据

### 2.1 代码差异

`git diff -- apps/desktop/src-tauri/src/widget.rs` 显示 `PositionMoveGate` 是本轮动物移动/防抖修复新增的结构：

- `write_lock: Mutex<()>`
- `animal_move()`
- `write_if_generation_current()`
- `place_if_generation_current()`

三个方法都会在持锁状态执行调用方传入的 closure，而 closure 内包含：

- `outer_position()`
- `inner_size()`
- `available_monitors()`
- `set_position()`
- `set_size()`

这些 Tauri 窗口 API 需要主事件循环响应。后台线程持锁等待主线程时，如果主线程也等待该锁，就会形成永久环。

关键代码位置：

- `apps/desktop/src-tauri/src/widget.rs:248`：`PositionMoveGate`
- `apps/desktop/src-tauri/src/widget.rs:642`：`set_widget_visible_edges`
- `apps/desktop/src-tauri/src/widget.rs:726`：`finish_widget_drag`
- `apps/desktop/src-tauri/src/widget.rs:747`：`move_widget_to`
- `apps/desktop/src-tauri/src/widget.rs:797`：`resize_widget_height`
- `apps/desktop/src-tauri/src/widget.rs:991`：`apply_position`
- `apps/desktop/src-tauri/src/widget.rs:1003`：锁内调用窗口 API
- `apps/desktop/src-tauri/src/widget.rs:1105`：retry 线程锁内调用 `outer_position()`

### 2.2 主线程栈

`sample` 报告 `/tmp/qiling-widget-sample.txt` 和 `/tmp/qiling-widget-sample-2.txt` 的主线程栈一致：

```text
com.apple.main-thread
  -> set_widget_visible_edges
  -> settle_current_widget_position
  -> apply_position
  -> PositionMoveGate::place_if_generation_current
  -> Mutex::lock
  -> _pthread_mutex_firstfit_lock_wait
  -> __psynch_mutexwait
```

第二次采样仍在相同位置，说明不是短暂停顿。

### 2.3 后台锁持有者

同一个采样报告中的后台线程：

```text
WidgetRuntimeState::new
  -> settle_worker
  -> settle_and_emit
  -> settle_current_widget_position
  -> apply_position
  -> PositionMoveGate::place_if_generation_current
  -> WryWindowDispatcher::outer_position
  -> Receiver::recv
  -> semaphore_wait
```

关键含义：

1. 后台线程已经持有 `write_lock`。
2. 它调用 `outer_position()`，等待主事件循环返回结果。
3. 主事件循环正在 `set_widget_visible_edges` 中等待 `write_lock`。
4. 主线程不空闲，后台线程永远拿不到结果；后台线程不释放锁，主线程永远拿不到锁。

### 2.4 触发路径

典型并发触发是：

```text
前端内容盒周期重测 / 拖拽结束
  -> set_widget_visible_edges 或 settle_worker
  -> apply_position

wander / 气泡高度 / 贴边重试
  -> move_widget_to / resize_widget_height / schedule_position_retry
  -> PositionMoveGate
```

前端调用入口：

- `apps/desktop/src/components/Widget.tsx:422`：`resize_widget_height`
- `apps/desktop/src/components/Widget.tsx:1549`、`:1569`：`finish_widget_drag`
- `apps/desktop/src/components/Widget.tsx:1683`：`set_widget_auto_hide`
- `apps/desktop/src/components/Widget.tsx:1803`：`set_widget_visible_edges`
- `apps/desktop/src/widget/useAnimalMobility.ts:196`：`move_widget_to`

`useAnimalMobility` 的每帧移动会 `await invoke("move_widget_to")`；主线程冻结后，下一帧不会排程，走动随之停止。

## 3. 历史踩坑与本问题的关系

### 3.1 原抖动根因

此前实测发现：

- wander 每 tick 回读窗口位置。
- 窗口服务器的实际移动滞后于写入。
- `schedule_position_retry` 又每 150ms 强制回推旧目标。
- 结果形成约 150ms 周期的往复振荡和“走 4 步退 3 步”。

### 3.2 当前锁为什么存在

`PositionMoveGate` 的目标是：

- 串行动物移动、settle 和 retry。
- 用 generation 阻止旧 settle/retry 覆盖新 wander 位置。

这个目标本身合理，不能因为死锁就把锁和 generation 全部删除。

### 3.3 本次错误

错误不在“要不要串行”，而在**锁作用域跨越了主事件循环依赖**：

```text
持锁
  -> 调 Tauri 窗口同步 API
  -> 后台线程等待主线程
  -> 主线程又等待锁
```

以后所有 Tauri 位置锁都必须遵守：

> 持有 `PositionMoveGate` 的线程不能等待主事件循环；主线程也不能无限等待一个可能等待主事件循环的锁持有者。

## 4. 解决方案对比

| 方案 | 改动 | 优点 | 风险/代价 | 建议 |
|---|---|---|---|---|
| A. 5 个入口改 `async fn` | 极小 | 保留锁和 generation 语义；主线程不再等待锁 | 后台阻塞会占用一个 Tokio worker，但窗口调用很短 | **推荐** |
| B. 锁全部改 `try_lock` | 小 | 可快速止血，主线程绝不等待 | 竞争时会跳过 settle 或拒绝一次移动，可能丢一次定位 | 备用应急 |
| C. 单一位置控制线程/队列 | 中大 | 所有窗口位置读写单一所有者，长期最稳妥 | 需要重写调用和返回语义，回归面较大 | 后续重构 |
| D. 删除锁或 retry | 极小 | 看似立即恢复 | 会重新引入此前抖动和旧位置覆盖新位置 | **禁止** |

### 4.1 推荐方案 A

只把下列 5 个 Tauri 命令从同步函数改为异步命令：

1. `set_widget_auto_hide`
2. `set_widget_visible_edges`
3. `finish_widget_drag`
4. `move_widget_to`
5. `resize_widget_height`

预期形态：

```rust
#[tauri::command]
pub async fn set_widget_visible_edges(...) -> Result<WidgetPreferences, String> {
    // 现有逻辑不变
}
```

原理：

- 同步 Tauri 命令在主线程执行，会直接参与死锁环。
- 异步命令由 Tokio 执行，可以在后台等待 `PositionMoveGate`。
- 主线程保持空闲，可以处理 `outer_position()`、`set_position()` 等窗口请求。
- 锁和 generation 逻辑保持原样，原有串行测试可以继续成立。

不建议顺手改其他命令或重构前端。

### 4.2 备用方案 B

如果方案 A 在当前 Tauri 版本上出现异步命令兼容问题，可将 `PositionMoveGate` 三个方法改为非阻塞获取锁：

- `animal_move` 锁忙时返回错误。
- `place_if_generation_current` 锁忙时返回 `Ok(None)`，跳过本次 settle。
- `write_if_generation_current` 锁忙时返回 `Ok(false)`，停止该轮 retry。

该方案能断开死锁，但会牺牲竞争时的一次操作，只作为短期止血。

### 4.3 长期方案 C

建立一个位置控制 actor：

```text
主线程 / settle / retry / wander
  -> 向位置队列发送请求
  -> 唯一 worker 读取和写入窗口位置
  -> generation 只在 worker 内更新
```

它能彻底消除窗口 API 与业务锁的交叉等待，但需要同时调整错误返回、重试和命令完成时机，不建议明天首刀直接做。
