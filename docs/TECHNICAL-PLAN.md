# DeskMate 技术方案

## 0. 方向收敛

DeskMate 的技术目标是支撑“角色化、本地优先、懂项目记忆的 AI 工作伙伴”，不是自研通用 Computer Use 平台。

技术实现优先保证：

- 语音交互自然、稳定、可打断
- 角色状态和任务状态一致
- 项目记忆可检索、可解释、可修改
- Codex、MCP 等现有执行器可以被统一调度
- 高风险操作有明确授权边界

桌面感知、浏览器自动化和实时全双工作为后续扩展，不作为 V1 的核心承诺。

## 1. 架构判断

当前更准确的目标架构是三层，而不是把所有功能都塞进一个桌面窗口：

```text
桌面运行时
  ├─ 透明挂件窗口
  ├─ 全局快捷键 / 系统托盘
  ├─ 权限申请
  └─ 打开默认浏览器中的主界面

浏览器主界面
  ├─ 主页
  ├─ 对话
  ├─ 记忆
  ├─ 知识库
  ├─ 我的智能体
  └─ 设置

本地 AI 服务
  ├─ LLM Gateway
  ├─ STT / TTS / VAD
  ├─ Project Memory
  ├─ Persona / State Machine
  ├─ MCP / Skill Registry
  └─ Agent Router
```

## 2. 桌面运行时选型

### 方案 A：Electron

- 优点：透明窗口、窗口管理、跨平台资料和示例多；官方文档支持透明窗口、置顶窗口和自定义拖拽区域。
- 缺点：体积较大；如果主界面坚持使用系统默认浏览器，Electron 的主要优势会被削弱。
- 适合：未来希望把主界面也收回桌面应用，或大量依赖 Node/Electron 插件生态。

### 方案 B：Tauri 2

- 优点：桌面窗口和 Web 前端分离更清晰，包体通常更轻；权限可以通过 capability 做边界控制。
- 缺点：需要 Rust；不同系统依赖各自 WebView，跨平台视觉细节需要验证。Windows 使用 WebView2，macOS 使用 WKWebView。
- 适合：挂件是原生常驻层，主界面明确在默认浏览器打开的产品。

### 初步建议

暂不立即锁死，但从当前需求看，优先评估：

`Tauri 2 + React/TypeScript + 本地 Python 服务 + 浏览器主界面`

如果后续发现需要大量 Electron 专属能力，再切换到 Electron。现有 Python 代码可以继续作为 AI 服务原型，不需要重复实现。

## 3. 浏览器主界面方案

主界面由本地 Web 服务提供，例如：

```text
http://127.0.0.1:<随机端口>/
```

桌面运行时负责：

- 启动或连接本地服务
- 生成一次性会话令牌
- 调用系统默认浏览器打开主界面
- 通过 WebSocket/SSE 接收任务状态

不建议直接依赖固定端口或无鉴权的本地接口。主界面和挂件需要共享事件总线，但浏览器页面不应拥有任意执行桌面操作的权限。

## 4. 模块边界

### 前端层

- 挂件窗口
- 主界面
- 设置页
- 对话页
- 记忆页
- 知识库页
- 智能体页

### AI 服务层

- LLM 调度
- STT
- TTS
- VAD
- 项目记忆存储、检索与摘要
- 角色配置和状态机
- 授权判断与事件回流

### 执行层

- MCP
- skill/plugin
- Obsidian 读写
- 浏览器只读工具
- 外部智能体转发

执行层不承担角色人格，不直接决定用户可见的交互状态；它只返回结构化进度、结果和风险信息。

## 5. 角色系统与状态机

角色系统由三部分组成：

- `PersonaProfile`：人设、语言风格、声音、边界
- `StateMachine`：空闲、聆听、思考、执行、授权、结果等状态
- `Renderer`：把状态映射到图片、序列帧、CSS 动画或 Live2D

推荐的事件流：

```text
用户输入
  → StateMachine.listening
  → StateMachine.thinking
  → Agent Router 判断任务类型
  → StateMachine.executing 或 speaking
  → StateMachine.awaiting_approval / completed
```

LLM 只产生结构化事件建议，最终状态由应用状态机确认，避免模型直接控制动画和权限。

## 6. 语音技术方案

“台湾腔”建议拆成可替换的语音配置：

- `locale = zh-TW`
- `voice = zh-TW-HsiaoChenNeural` 等具体声音
- 角色词汇与语气规则
- 语速、停顿、情绪强度

Azure Speech 当前提供 `zh-TW` 中文（台湾普通话、繁体）语音，因此第一版不需要训练专属声音即可验证产品效果。

后续再评估本地 TTS、定制声音和音色授权。不要把“地区语音”与“声音克隆”混为同一项能力。

## 7. 第一版实现顺序

1. 统一数据结构和模块接口
2. 做挂件与浏览器主界面
3. 做文字与语音对话闭环
4. 做设置和基础角色配置
5. 做最小项目记忆与 Obsidian 只读检索
6. 做简单/复杂任务分流
7. 接入 Codex Agent Adapter
8. 再扩展浏览器和桌面自动化

## 8. 关键风险

- 语音全双工复杂度高
- Live2D 会显著抬高成本
- 桌面自动化涉及权限与稳定性，因此 V1 只保留外部执行器集成
- 过早堆叠多智能体会把产品变成调度平台，而不是助手
- 记忆如果没有来源、时间和编辑能力，会降低用户信任

## 9. 设计原则

- 先有产品感，再补能力
- 先收敛到 MVP，再扩展
- 先让挂件和语音好用，再让工作能力变强
- 先把项目记忆做成可用闭环，再扩展通用自动化
- 所有外部能力都必须经过统一调度层
