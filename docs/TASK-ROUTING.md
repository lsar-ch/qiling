# 栖灵 任务分流规则

## 1. 目标

把用户输入分成四类：

- 纯问答
- 前台可执行任务
- 后台复杂任务
- 高风险任务

这样 栖灵 才能决定是直接回答、自己做、交给后台做，还是先请求授权。

## 2. 分流维度

任务分流不只看“工作量大小”。

建议同时看三个维度：

- 风险
- 复杂度
- 执行时长

## 3. 分类规则

### 3.1 纯问答

特征：

- 事实查询
- 概念解释
- 文本总结
- 日常聊天

处理方式：

- 前台直接回答

### 3.2 前台可执行任务

特征：

- 操作路径清楚
- 风险低
- 步骤少
- 可快速回显结果

例子：

- 打开网页搜索
- 点击页面按钮
- 展示结果
- 简单整理信息

处理方式：

- 前台执行

### 3.3 后台复杂任务

特征：

- 多步骤
- 多工具
- 需要规划
- 需要长时间执行
- 适合交给 Codex 或其他 Agent

例子：

- 改代码
- 批量处理任务
- 跨应用协作
- 需要持续跟踪状态的任务

处理方式：

- 交给后台 Agent

### 3.4 高风险任务

特征：

- 删除
- 发送
- 支付
- 提交
- 修改配置
- 外部副作用明显

处理方式：

- 必须先授权

## 4. 判定顺序

推荐顺序：

1. 先看是否高风险
2. 再看是否只是纯问答
3. 再看是否可前台快速完成
4. 否则交给后台 Agent

## 5. 判定结果

分流结果建议统一成结构化状态：

- `answer`
- `execute_frontend`
- `delegate_backend`
- `request_approval`

这样后续语音链路、挂件状态机、Agent Router 都可以共用同一套结果。

## 6. 当前落地实现（`services/ai-service/app/routing/classifier.py`）

现状是**纯规则匹配（正则 + 字符数），不接模型**，命中即定，顺序如下：

1. `_HIGH_RISK_PATTERNS` 命中（删除/移除/清空/支付/转账/提交/发送/发布/修改配置/改密码…）→ `request_approval`，`risk=high`。
2. 命中 `_ANSWER_HINTS`（是什么/怎么/为什么/解释/总结/分析/什么意思/在吗/你好…）、含 `?`/`？`，或**短句**（去空格 ≤ 12 字且不含后台词与动作词）→ `answer`，`risk=low`。
3. 命中 `_FRONTEND_HINTS`（打开网页/搜索/点击/滚动/复制/粘贴/浏览一下…）→ `execute_frontend`。
4. 其余 → `delegate_backend`。`risk=medium` 需命中 `_BACKEND_HINTS`（代码/项目/文件/测试/文档/依赖/版本/构建/错别字…）**或** `_ACTION_HINTS`（查一下/改一下/整理/检查/修复…）；否则 `risk=low`。

判定真实指令 vs 普通聊天的实际依据：

- **动作词**：出现「查一下/改一下/整理/检查/修复」这类明确动词 → 按任务处理。
- **对象词**：出现「代码/项目/文件/文档/依赖/版本」这类工作对象 → 按任务处理（`medium`）。
- **短句 + 无动作无对象**：「就是你看那个落花生。」这类顺口一说 → 按闲聊处理。
- 泛化前缀「帮我/请帮/给我」本身**不算**指令特征（「帮我倒杯水」仍是闲聊），避免闲聊被误判成任务。

`risk_level` 的两处作用：`confirm_risky` 下只有 `high` 需要授权；对话页只对
`delegate_backend` 且 `risk != low` 的任务自动起跑，`low` 只记进任务台、需手动运行。
