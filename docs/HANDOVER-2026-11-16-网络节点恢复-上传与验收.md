## 4. 需要特别注意的事项

- 不要使用 v0.1.0 安装包作为 v0.2 验收输入。
- 不要直接用改 `app.qiling.desktop` bundle id 的方式隔离版本，会断开运行数据和升级链。
- macOS 已有运行数据目录中的 `.seed-version` 是 `0.2.0`，旧模板不会自动覆盖。若本机已跑过旧包，验收前需要手动刷新 `~/Library/Application Support/app.qiling.desktop/apps/web/dist`，或使用全新运行数据目录测试。
- 当前包是 ad-hoc 签名，未公证；首次打开的安全提示属于预期行为。
- 当前 GitHub Release 的 x64 DMG 已来自本地未提交工作区；在源码整理完成前，不把它当作已完成的可追溯发布收口。
- v0.1 历史资料已归档到 `docs/history/v0.1/`；旧原型在 `archive/legacy-v0.1/`；本地大产物在 ignored 的 `archive/local-only/v0.1/`。

## 5. 验收标准

1. x64 macOS、arm64 macOS、Windows 产物均可从 Release 或 artifact 通道稳定下载。
2. 所有平台产物名称、版本和 SHA-256 与发布清单一致，且构建输入可追溯到远程 commit。
3. 最终 macOS 包启动正常，挂件气泡、空格输入、拖动、双击和蓝猫外观均通过。
4. Windows 真机验收按任务卡完成，阻塞项为零或已明确处理。
5. Release 资产、tag、远程 main 和验收文档互相一致。

## 6. 风险与异常

| 风险 / 异常 | 影响 | 处理 |
| --- | --- | --- |
| 网络节点仍未恢复 | 无法上传、下载或创建 Release | 保持本地产物与清单，按节点恢复时间继续 |
| artifact 下载校验失败 | 不能进入真机验收 | 停止验收，记录错误，重新构建或下载 |
| Release 资产与源码 tag 不一致 | 无法证明下载包对应哪次源码 | 先整理并提交候选改动，再重新构建并覆盖对应资产 |
| macOS arm64 资产缺失 | Apple Silicon 用户无法下载本版原生包 | 触发 arm64 workflow，完成真机抽检后上传 |
| Windows 资产未做真机回归 | Windows 发布质量未知 | 使用现有 x64 安装包完成完整回归并回填证据 |
| macOS 旧运行数据不刷新 | 维护界面或挂件表现不一致 | 刷新 web dist，或使用全新运行数据目录复测 |
| Windows 角色资产或工作台数据异常 | 验收阻塞 | 按 Windows 任务卡回传日志和截图，定位后重测 |
| 签名或安全提示异常 | 安装受阻 | 保留提示和系统版本，按未公证包说明处理，不擅自绕过安全策略 |
