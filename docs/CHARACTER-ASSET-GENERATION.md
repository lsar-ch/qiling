# 角色资产生成路线决策（2026-09-11）

> 状态：方向已定，V1 按「单张基础形象 + 程序化动态」落地
> 起因：用户实测「提示词 → 文生图 → 分层件」不可用；代码侧对素材的像素分析证实了原因。

## 2026-09-12 去背景验收记录

当前 V1 使用边缘连通背景清理，只承诺处理主体清晰、背景单一的基础形象：

- 猫角色：白色毛发与背景颜色接近，身体白色区域被错误转为透明。
- 人物角色：椅子腿之间的封闭白色区域不与画布边缘连通，因此未被转为透明。
- 结论：单一颜色阈值加边缘 flood fill 无法同时可靠处理白色主体和封闭孔洞；复杂背景不作为 V1 的可用输入。
- V1 处理：透明图直接裁切；PNG/JPG/WebP 单色背景通过边缘连通去背景，随后统一输出 `1024×1024` 固定画布，主体底部居中并保留 48px 安全边距。
- 后续方向：引入主体分割/语义抠图，或允许用户在预览页用“保留/删除”笔刷修正蒙版。

## 1. 结论

**V1 不再以「AI 文生图拆层」作为角色资产生成主路径。**

用户只需要确认一张基础形象。V1 由完整图和程序化动态提供可用的角色体验，不要求用户准备多张状态图或组件图。后续完整状态帧、半自动分层和骨骼定位均为渐进式增强。

- 主形象：单张完整立绘（用户已交付，白底抠图流程已跑通，当前挂件即此方案）
- 用户形象生成：允许用户使用外部或 栖灵 内部图像工具生成一张高清完整图，再导入确认
- 栖灵 资产处理：自动检测、去背景、清理、裁切、对齐和缩放，生成自己的资产 manifest
- AI 生图降级为「可选输入来源」，不承担拆层、状态帧一致性或动画资产生产

## 2. 为什么文生图路线不可行（证据）

用户用商品文生图工具按提示词产出分层件，实测不可用；对交付素材（`~/Desktop/未命名文件夹/`）逐像素分析：

| 检查项 | 实测结果 | 影响 |
| --- | --- | --- |
| 透明通道 | 6 张全为 RGB 无 alpha（白底） | 叠放必然出现白块/毛边 |
| 背景 | 近白但带全幅稀疏噪点（1-2% 像素偏离） | 抠图后仍有脏点，需浮填去噪 |
| 部件尺寸 | 眼睛/嘴仅占画布 1-2%（约 100-200px） | 缩到挂件 150px 时不可辨认 |
| 对齐 | 部件位置与 body 脸部无法保证锚点一致 | 眨眼/口型必然错位 |

根因：文生图输出的是「一张画」，不掌握「透明图层、部件坐标系、角色一致性」这些结构性信息；提示词只能软约束，无法保证。

## 4. 后续备选：参数化 SVG/Canvas 角色生成器

这不是 V1 的前置方案，也不是当前用户流程。只有当 V1 的完整图程序化动态已经验证，且用户确实需要更丰富的局部动作时，才评估是否增加模板生成器。

### 为什么可靠
- SVG 部件 = 代码元素：透明、任意缩放、锚点天然精确，眨眼/嘴型/表情直接 CSS/DOM 驱动
- 与现有挂件技术栈完全一致（原版猫就是内联 SVG + CSS keyframes，动得很自然）
- 多角色 = 换参数（肤色/发色/发型/服装配色/眼型/嘴型/配件），零资产生成成本

### 可能的后续结构
```text
角色描述 / 可选参考图
  → 特征抽取或模板选择
  → 参数化 SVG/Canvas 实例化
  → 输出可动画的程序化角色
```

`layers.json`、部件锚点和模板参数只属于后续内部实现，V1 不要求用户看到、编辑或确认这些内容。

### 参考图驱动的原理与保真度边界

原理：用户给一张喜欢的角色图，视觉模型（VL）抽取**结构性特征**，而不是逐像素复制：

| 特征 | 抽取方式 | 落到生成器 |
| --- | --- | --- |
| 色板（发色/瞳色/主色/辅色） | VL 识别 + 图像取色 | 模板配色参数 |
| 发型类别 | VL 分类（长发/短发/双马尾/单马尾/刘海形态…） | 发型模板选择 |
| 眼型/眉眼 | VL 分类（圆眼/细长眼/下垂眼…） | 眼部部件参数 |
| 服装类型与配色 | VL 分类（西装/连衣裙/卫衣…） | 服装部件 + 配色 |
| 配件 | VL 识别（发夹/耳机/围巾/眼镜…） | 可选配件图层 |

边界（必须对用户说清）：
- 输出是「同一风格气质的参数化角色」，不是参考图的 1:1 复刻
- 复杂细节（复杂发型分层、花边、文字、LOGO、多物件堆叠）会简化或省略
- 小尺寸挂件（约 150px）下可辨认为主：发型 + 色板 + 眼型 + 服装主色抓住，感知上就「对味」
- 参考图质量要求：正面或 3/4 侧、上半身或全身、无大面积遮挡、画风干净的图效果最好

### 参考图覆盖度处理（2026-09-11 确认）

参考图构图决定抽取范围，未覆盖部分一律用模板默认并明示：

| 参考图构图 | 抽取范围 | 缺失部分处理 |
| --- | --- | --- |
| 头部特写 | 发色/发型/瞳色/眼型/眉形/面型/配饰 | 身体 + 服装 = 默认模板 |
| 半身 | 面部 + 领口/衣服主色（可见范围尽量抽） | 下半身 = 默认模板 |
| 全身 | 全部特征 | 无（理想输入） |

- VL 输出带「覆盖度标注」：哪些特征来自参考图、哪些是默认；生成的角色卡明示「身体为默认模板，可换服装」
- 支持用户用一句话补充缺失信息（如「穿黑色连衣裙」），合入参数后再实例化
- 结果形态：头身比正常的小人（不会是大头）——头部特征决定观感，挂件小尺寸下「脸对味」即达成

为什么不做「参考图 → AI 生图 → 拆层」：与文生图拆层同一根因（白底/噪点/部件错位/一致性差），已否决（见 §2）。

### 与 V1 立绘方案的关系

- V1 主模式：`artwork`，用户导入或生成一张完整基础形象，状态表达用程序动效和 overlay
- 后续可选模式：`svg` 或其他程序化渲染器，必须复用同一套业务状态、表现事件和角色卡配置
- 两种模式都不能让 栖灵 依赖 Codex、WorkBuddy 或某个外部生图工具

## 5.1 分层资产契约（2026-09-19 定稿）

资产生成路线重开后按 `layers.json` v1 交付（现有单图模式保留为回退）：

- `layers[]`: `{id, file, z, role}`，`z` 升序 = 从底到顶叠放（alpha 合成可复现 `main.png`）
- `role` = T4 动作分组：`eyes` / `mouth` / `hair_front` / `hair_back` / `face` / `body` / `accessory`；同 role 多图层（如眼睛的多部件）作为一组做整体变换
- `stage` / `motions` 字段与 default 包兼容；无分层时回退单张 `main.png`
- 后端经 `GET /api/personas/{id}/asset/{path}` 提供文件（禁止路径穿越）；挂件 `fetchPersonaAssetManifest` 读取并按 z 叠放
- role 动画：眼睛 `dmBlink`、说话 `dmMouthTalk`、前后发 `dmHairSway`、配饰 `dmAccessoryFloat`，整体动作仍走 `data-action` 上的全局 keyframes
- 首个测试包：`data/persona-assets/qianwen_t4/`（19 层，v0 已知问题见包内 README，等 1024 半身重跑替换）

### 5.2 多帧 / spritesheet 扩展（2026-09-22）

`layers.json` v2 在 v1 基础上增加两个可选块，均不影响旧包：

- 单层多帧：`layers[].frames = { "<state_name>": ["layers/mouth_0.png", ...] }`，可选 `frame_fps = { "<state_name>": 8 }`；状态名与动作触发器一致（idle/listening/thinking/speaking/executing/awaiting_approval/success/error 等）。
- 全身 spritesheet：顶层 `spritesheets = [{ "state_name": "idle", "file": "sprites/idle.png", "frame_width": 512, "frame_height": 512, "frames": 8, "fps": 8 }]`；优先于分层渲染，无匹配状态时回退 layers / main.png。

挂件渲染优先级：VRM > 当前状态 spritesheet > 分层 frames > 单图。
