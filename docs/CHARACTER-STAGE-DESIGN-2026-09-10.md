## 1. 讨论一：角色级表现用什么展示、如何生成

### 1.1 问题

角色卡目前把「形象、声音、唤醒」收口成启用即整套生效；下一步要把角色卡关联的「动态效果配置」落到角色级表现上。需要回答：每套角色的表现**用什么介质渲染**（展示层），**资产如何生产**（生成管线）。

### 1.2 现状锚点（代码与文档证据）

- **角色卡字段现状**：`PersonaPayload` 仅有 `id / name / kind / description / personality / backstory / language / reply_style / avatar / voice / activation`（`services/ai-service/app/api/settings.py`）。`avatar` 是单张图/URL，尚无「可动部件」和「表现配置」字段。
- **挂件展示层现状**：内联 SVG 吉祥物 + CSS keyframes（呼吸 `breatheBody`、眨眼 `blink`、光环 `aura`、状态徽章等），由程序状态机驱动；状态含 `idle/listening/thinking/speaking/executing/awaiting_approval/completed/interrupted` 共 8 态。见 `apps/desktop/src/components/Widget.tsx`、`apps/desktop/src/components/widget.css`、`docs/WIDGET-STATE-MACHINE.md`。mascot 目前硬编码同一只猫，不随角色卡变化。
- **资产方向已收敛**：V1 先用单张完整立绘（PNG/WebP）配合 CSS/Canvas 程序化动态；分层 2D、状态帧和 Live2D 均后置。

结论：**「状态怎么动」的骨架已有，缺的是「每个角色画什么、动哪些部件、用什么情绪配色」的 per-character 资产与配置。**

### 1.3 展示介质三路线对比

| 路线 | 做法 | 优点 | 缺点 | V1 判断 |
| --- | --- | --- | --- | --- |
| A. 组件化 SVG | 每角色一套内联 SVG 组件，部件 = SVG 元素，复用现有 CSS 动画 | 最轻、缩放清晰、无需资产管线 | 写实/精致度受限，画风统一依赖手绘 | 保留（沿用吉祥物风格时可走） |
| B. 分层位图 + 程序动画 | 主立绘 PNG/WebP + 独立部件（眼睛 ×2、嘴 ×3 帧、腮红/特效）；CSS/JS 做呼吸、眨眼、嘴型帧切换 | 有立绘质感、资产可换装复用、分层不锁渲染、可迁 Live2D | 需要拆层规范与命名管线 | **V1.5/V2 后置** |
| C. 帧动画 Sprite Sheet | 每状态一组帧序列，定时器/主循环播放 | 表现力强、实现直接 | 资产体积与维护成本高、难换装、帧间易不稳 | 仅口型/眨眼等小部件采用 |
| D. Live2D / 3D | 骨骼/3D 渲染 | 表现力最强 | 违背 V1 轻量约束 | 后置；仅要求资产分层不锁渲染技术 |

### 1.4 历史生成管线建议（已降级为后续方案）

```text
完整基础形象
  → DeskMate 自动检测、去背景、清理、裁切、对齐、缩放
  → 输出 asset-manifest.json
  → V1 程序化动态与状态 overlay

只有在 V2/V3 需要局部动画时，才进入：

  → 半自动识别部件
  → 人工确认分层
  → 内部生成 layers.json
```

约束与校验：

- **AI 直出图不当最终可动画资产**（帧抖动、锚点不稳、图层错位），这是 `docs/WIDGET-ASSET-PLAN.md` 的既定纪律。
- 关键校验点：缩到挂件实际尺寸（mascot 约 150px）仍可辨认；透明边缘干净；部件锚点与现有舞台 `viewBox 200x200` 坐标体系对齐。

### 1.5 角色卡配置模型（presentation 块）

给 `PersonaPayload` 增加 `presentation`（或 `stage`）配置块，把散落效果收口为配置而非硬编码：

- `theme`：主色 / 光环色 / 情绪色（角色卡、气泡、aura 跟随）；
- `parts`：部件资产引用 + 锚点（身体/眼睛/嘴）；
- `motions`：`idle/listen/think/talk/run/wait/done` 各自引用动画名与参数（节奏、幅度、嘴型帧）；
- `fx`：情绪特效开关（思考气泡、音符、完成闪光等），可与语音 `emotion` 标签联动。

目标语义：**启用角色 = 身份 + 声音 + 唤醒 + 表现，一套生效**；挂件与 Home 放大展示读同一份 `presentation`。

### 1.6 后续试点组合（V1 之后）

路线 B + `presentation` 配置块，作为 V1.5/V2 的增强验证：

1. 先验证单张完整图的 `idle / listening / speaking` 程序化表现；
2. 再选择可靠部件做最小分层；
3. 验证「换角色 = 换立绘 + 换主题色」的配置驱动能力；
4. 后续再扩充部件数量和状态种类。

## 2. 讨论二：外部桌宠架构材料的可吸收性分析

### 2.1 材料概述

外部材料提出四层架构：

1. **素材渲染**：AI 视频抽帧或逐帧精灵表，推荐 Spine/Live2D 做 2D 渲染；亦可粒子特效应付施法。
2. **状态中枢与事件驱动**：FSM 管理状态（idle/interact/rest/drag…）；Agent Hooks 桥接脚本把后台状态 POST 到本地端口（示例 127.0.0.1:4271），桌宠据此切动画与气泡。
3. **智能行为决策**：随机矩阵（Stochastic Matrix）定义状态转移概率、保持动作惯性；多轨道动画编排（AnimComposer）做基础动作层 + 表情层 + 特效层，CrossFade 平滑过渡。
4. **角色卡状态数据自动更新**：后台回复末尾输出含 `op/path/value` 的 JSON 指令数组，桌宠解析后改本地角色状态变量表（好感度、饱食度、情绪），UI 内嵌 HTML/CSS 可视化。
5. **总结建议**：先搭「状态机 + 动画库」，本地端口收 JSON 指令切状态；再逐步加随机矩阵与多轨道动画；可直接用 DyberPet / Ark-Pets 等现成框架。

### 2.2 总体判断

- 四层划分是桌宠通用架构，方向正确。
- 但材料面向 DyberPet / Ark-Pets 一类**游戏化桌宠**，而 DeskMate 定位是「角色化、本地优先、懂项目记忆的 AI 工作伙伴」。
- 其中约一半内容我们已有等价实现；照单全收会引入游戏化复杂度，违背 V1「轻量 2D、无 Live2D/3D」约束。

### 2.3 逐条对照（已有 / 可吸收 / 建议暂缓）

| 外部建议 | 判断 | 理由与落地方式 |
| --- | --- | --- |
| AI 视频抽帧 → 精灵表；Spine/Live2D | 方向对，打折吸收 | 视频帧形体不稳定、无法分层换装，会破坏资产复用前提。主体走「立绘 + 部件 + CSS/JS 动画」；轻量帧只用于口型/眨眼；Spine/Live2D 作为后置渲染器，资产分层结构保持兼容 |
| FSM + Agent Hooks POST 本地端口（4271） | **已有等价** | 已有程序事件驱动的 8 态 FSM 与事件链路（语音/聊天/任务/AgentRun）。不另起 4271 平行通道；应把现有链路整理成统一「表现事件流」（状态 + 情绪 + 气泡 + 主题色） |
| 随机矩阵 + 多轨道 CrossFade | **最有价值，分期吸收** | 轨道分层（身体基础层 + 表情层 + 特效层）与现有 SVG 的 `body/eyes/mouth/aura/badge` 分层天然吻合，用 CSS 类切换 + 过渡即可平滑。随机矩阵等状态与动画足够多后再上；V1 先做 idle 小随机微动作 |
| 回复末尾 JSON（op/path/value）改好感度/饱食度 | **不建议照搬** | ① 养成数值不符合产品方向；② 违反「表现由程序状态驱动、LLM 不直接控动画」的设计原则；③ 解析聊天流 JSON 脆弱、耗 token。情绪应从真实信号（任务结果、`voice.emotion`、激活状态）推导；确有需要就走结构化事件通道 |
| 先框架后增强的推进顺序 | 采纳 | 与项目路线图一致（基础状态机 + 动画库先行，随机矩阵/多轨道后续） |

### 2.4 收敛结论（回应讨论一）

外部材料给出的是行业通解；落到 DeskMate 应收敛为：

- **展示**：轻量立绘/部件 + 状态机 + 分层 CSS 动画；
- **生成**：imagegen 设定图 → 人工规范拆层 → `assets/personas/<id>/` + `layers.json`；
- **事件通道**：复用现有本地服务链路，不新增平行端口；
- **角色内在状态**：从真实运行信号推导，V1 不做养成数值。

「随机矩阵 / 多轨道 CrossFade / 视频抽帧精灵表」标记为 V1 验证通过后的增强项，不提前排期。

### 2.5 落地建议

近期只做两件事：

1. 把现有状态事件整理成统一的**表现事件载荷**（状态/情绪/气泡/主题色）；
2. 做一个示范角色的「立绘 + 眼嘴部件」试点，验证 idle / 听 / 说三态联动。

其余项写入路线图或 `docs/WIDGET-ASSET-PLAN.md` 后续方向，避免结论丢失。

## 3. 决策汇总（2026-09-10 已拍板）

### 决策 1：角色风格可配置 ✅

`presentation.style` 支持 `"human" | "animal"`，渲染侧按类型走不同动画预设（人物：身体前倾/手势；动物：耳朵/尾巴等部件）。分层资产结构不变，仅动画映射表不同。

### 决策 2：资产生成走「基础形象 + 渐进式增强」方案 ✅

不要求用户自己制作组件，也不把 AI 自动拆层作为 V1 前置条件：

- 用户提供或生成一张高清完整基础形象
- DeskMate 自动去背景、清理、裁切、对齐和缩放
- V1 用完整图 + 程序化动态表达状态和互动
- V1.5 可选生成完整状态帧，由 DeskMate 统一规范化
- V2 再评估半自动部件识别与分层
- V3 再评估骨骼、网格和 Live2D 类渲染

详细用户流程和版本边界见 `docs/CHARACTER-INTERACTION-ROADMAP.md`。

对比自建管线：开发成本极低、用户自由度高、资产质量用户自控、V1 上线快。

不再把提示词模板定稿作为 V1 阻塞项；用户可使用任意外部工具生成基础图，DeskMate 只对导入结果做规范化和验收。

### 决策 3：挂件简化构图看实际效果 ✅

挂件实际约 150px 渲染尺寸，先以完整图缩放后的辨识度为验收基准。`layers.json` 不属于 V1 用户侧产物，待 V2/V3 分层时再定义。

### 决策 4：表现事件流排期 ✅

统一表现事件载荷 schema、后端桥接和挂件消费已完成，当前转入角色资产导入和真实挂件表现调优。详细状态见 `docs/PROJECT-ROADMAP.md`。

### 明确采纳 / 暂缓 / 不采纳

- **采纳（V1 内）**：完整图展示介质；`presentation` 配置块；统一表现事件流；单张基础形象导入；程序化动态；人物/动物动作预设；轻互动事件。
- **暂缓（V1 后）**：随机矩阵；多轨道 CrossFade 增强；完整状态帧生成；口型/眨眼轻量帧精灵表；半自动拆层；更多角色资产。
- **不采纳（V1）**：AI 视频抽帧做主体动画资产；本地 4271 平行事件端口；好感度/饱食度养成数值；解析 LLM 回复 JSON 改状态；强制用户制作分层组件；依赖 Codex/WorkBuddy 才能运行。

## 4. 排期：表现事件流

### 4.1 为什么现在做

表现事件流是连接「后端状态」↔「挂件渲染」的唯一桥梁。事件 schema 不定，后续所有角色表现实现（挂件读配置、部件切换、主题色跟随）都无法开工。当前 Step 9 视觉打磨接近收尾、八页导航上线，正是切入时机。

### 4.2 建议节奏

| 阶段 | 内容 | 预计 |
|---|---|---|
| **已完成** | 表现事件 schema、后端事件发布、挂件消费、情绪动效 | 2026-09-11 |
| **当前** | 单张基础形象导入、manifest、人物/动物动作预设接入 | V1 |
| **下一阶段** | 可选完整状态帧与单状态重生成 | V1.5 |
| **后续** | 半自动分层、`layers.json`、骨骼/网格 | V2/V3 |

### 4.3 依赖关系

```
表现事件 schema / 后端桥接 / 挂件消费
    └── 单张基础形象导入 + manifest
            └── 程序化动态与轻互动验收
                    └── V1.5 完整状态帧
                            └── V2/V3 分层与骨骼
```
